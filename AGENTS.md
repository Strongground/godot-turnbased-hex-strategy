## Architecture Notes
- Core gameplay scripts are primarily in `classes/`.
- Scene-specific managers and menu flow are in `scenes/`.
- Data/content is theme-driven under `themes/` (example themes included).
- Utility/dev scripts live in `devtools/` and `tools/`.
- Whenever changes to the YAML-based theme-data was made, the corresponding JSON files are (re-)generated by using the `devtools/yaml_to_json.py` script.
- JSON is only data storage. The annotated source of truth is the YAML files which are designed to be human-friendly for editing and reading.
- External plugin exists in `addons/carmel4a97.RTS_Camera2D/`.

## Async Manager Initialization Pattern (NEW)
To prevent timing/race condition issues between Manager classes, all managers now use an async initialization pattern with Godot 4.6's `await` system:

### Manager Base Class
- All managers extend `GameManager` (in `classes/game_manager.gd`)
- `GameManager` provides:
  - `initialize() -> Future`: Main initialization entry point that awaits dependencies
  - `_initialize_internal() -> Future`: Override for manager-specific setup
  - `add_dependency(Node)`: Register dependencies on other managers
  - `is_initialized() -> bool`: Check if manager is ready

### Initialization Order (based on dependencies)
1. **SettingsManager** (no dependencies)
2. **ThemeManager** (no dependencies, provides data to others)
3. **PlayerManager** (no dependencies)
4. **WeatherManager** (no dependencies)
5. **FactionManager** (depends on ThemeManager)
6. **SfxManager** (depends on ThemeManager)
7. **MusicManager** (depends on SettingsManager, ThemeManager)

### Usage Pattern
```gdscript
# In any manager:
func _ready():
	pass  # Keep empty - initialization happens via initialize()

func _initialize_internal() -> Future:
	# Await dependencies in dependency order
	if dependency_mgr != null and dependency_mgr.is_instance_valid(dependency_mgr):
		await dependency_mgr.initialize()
	
	# Do manager-specific initialization
	_debug_log("Manager initialized")
	return true

# In game setup:
func _ready():
	await _initialize_managers()
	# Now safe to use all managers
	_setup_game()

func _initialize_managers() -> Future:
	await settingsMgr.initialize()
	await themeMgr.initialize()
	await playerMgr.initialize()
	# ... etc
	return true
```

### Manager Classes
- `classes/game_manager.gd`: Base class for all managers
- `classes/theme_mgr.gd`: Theme/data loading (extends GameManager)
- `scenes/PlayerManager.gd`: Player creation and management (extends GameManager)
- `scenes/FactionManager.gd`: Faction data management (extends GameManager, depends on ThemeManager)
- `scenes/WeatherManager.gd`: Weather effects and system (extends GameManager)
- `scenes/SettingsMgr.gd`: Settings and volume control (extends GameManager)
- `scenes/SfxManager.gd`: Special effects management (extends GameManager, depends on ThemeManager)
- `scenes/MusicManager.gd`: Music playback (extends GameManager, depends on SettingsManager, ThemeManager)

## Manager Blueprint (NEW)

### Creating a New Manager Class

Use this template when creating a new manager class to ensure consistency with the async initialization pattern:

```gdscript
extends "res://classes/game_manager.gd"

# member vars here
@export var game: Node
@export var themeMgr: Node
var my_data = {}

func _ready():
	# Keep empty - initialization happens via initialize() method
	pass

func _initialize_internal() -> Future:
	# Wait for dependencies (if any)
	if game != null and game.is_instance_valid(game):
		_debug_log("_initialize_internal(): Awaiting game initialization")
		# await game.initialize()  # Only if game is also a manager
	if themeMgr != null and themeMgr.is_instance_valid(themeMgr):
		_debug_log("_initialize_internal(): Awaiting themeMgr initialization")
		await themeMgr.initialize()
	
	# Perform manager-specific initialization
	_debug_log("_initialize_internal(): MyManager ready")
	return true

# Manager methods here
func my_method():
	# Your manager functionality
	pass
```

### Dependencies Chart
Before creating a new manager, determine its dependencies:
- No dependencies: SettingsManager, ThemeManager, PlayerManager, WeatherManager
- ThemeManager: FactionManager, SfxManager
- SettingsManager + ThemeManager: MusicManager

### Key Rules
1. **Never do work in `_ready()`** - Move all initialization to `_initialize_internal()`
2. **Always call `await`** for dependencies before doing your own setup
3. **Return `true`** from `_initialize_internal()` on success
4. **Use `is_instance_valid()`** checks before accessing exported nodes
5. **Emit `initialized` signal** automatically (handled by GameManager base class)

### Example: Adding a New Manager

If you need to add a new manager like `CameraManager` that depends on SettingsManager:

```gdscript
extends "res://classes/game_manager.gd"

@export var settingsMgr: Node

func _initialize_internal() -> Future:
	if settingsMgr != null and settingsMgr.is_instance_valid(settingsMgr):
		await settingsMgr.initialize()
	
	# Initialize camera system
	_debug_log("CameraManager ready")
	return true
```

## Observed Coding Patterns
- GDScript naming is mostly `snake_case` for vars/functions.
- Configurable values are frequently exposed through `@export`.
- Debug output is commonly funneled through local helpers (e.g. `_debug_log`).
- Scene wiring uses `find_child`, `@onready`, and `get_node_or_null` patterns.
- Runtime entity grid snapping should not happen directly in entity `_ready()`. `classes/game.gd` now emits `setup_complete` after `_setup_game()`, and entities snap once that signal fires so hex-centering data is available.
- During `_setup_game()`, runtime entities are explicitly snapped before `entities = _create_entity_list()` so click hit-testing and stored `grid_pos` values match the visible in-game positions.

After relevant code changes:
1. Open project in Godot and ensure scripts parse without errors.
2. Run the game from main menu (`MainMenu.tscn`) and load a scenario.
3. Perform a short smoke playthrough (selection, movement, basic combat/action buttons).
4. If theme data changed, verify parsing/loading path via menu selection and runtime logs.

### CLI validation (local)
- Verified binary in this workspace: `godot461`.
- Basic startup check: `godot461 --headless --path . --quit`
- Entry-scene startup check: `godot461 --headless --path . --scene res://scenes/MainMenu.tscn --quit-after 30`
- Scenario headless check with writable temp user-dir: `tools/run_scenario_1_headless.sh`
- The scenario runner defaults to `/tmp/godot-turnbased-hex-strategy-userdata` and overrides `HOME`, `XDG_CONFIG_HOME`, and `XDG_DATA_HOME` so Godot always has a writable user directory during CLI validation.
